# Issue: Persistence: auth token tables, entities and repositories

## Description

Part of epic #84; depends on #86 (organizations and users). Create the four authentication tables with their entities and repositories, following [persistence.md](docs/agents/specs/persistence.md) and the table specs [refresh-tokens.md](docs/agents/specs/organizations/data-model/refresh-tokens.md), [password-reset-tokens.md](docs/agents/specs/organizations/data-model/password-reset-tokens.md), [authorization-requests.md](docs/agents/specs/organizations/data-model/authorization-requests.md) and [account-edit-lockouts.md](docs/agents/specs/organizations/data-model/account-edit-lockouts.md).

## Problem

The session, recovery, device-authorization and account-edit endpoints need their tables and a typed, digest-only data access layer. None of it exists yet: after #86, `source/migrations/` holds only `organizations` and `users`.

## Expected Behavior

- `composer db:migrate` creates `refresh_tokens`, `password_reset_tokens`, `authorization_requests` and `account_edit_lockouts` exactly as their table specs define them, and `composer db:status` shows nothing pending or edited.
- Each table has a `final readonly` entity with `fromRow()` and a repository exposed through a memoized `Container` getter.
- Only SHA-256 digests reach the repositories and entities; no plain token is stored, passed or logged.

## Solution

### Migrations

- `0003_create_refresh_tokens.sql`, `0004_create_password_reset_tokens.sql`, `0005_create_authorization_requests.sql`, `0006_create_account_edit_lockouts.sql`, following [schema-migrations.md](docs/agents/specs/persistence/schema-migrations.md): one `CREATE TABLE` per file, explicit engine/charset/collation, no `IF NOT EXISTS`.
- Explicit names: `uq_<table>_<column>`, `ix_<table>_<column>[_<column>]`, `fk_<table>_<column>`. Every FK is `ON DELETE RESTRICT`.
  - `refresh_tokens`: `uq_refresh_tokens_token_hash`, `ix_refresh_tokens_user_id`, `ix_refresh_tokens_session_uuid`, `fk_refresh_tokens_user_id`.
  - `password_reset_tokens`: `uq_password_reset_tokens_token_hash`, `ix_password_reset_tokens_user_id`, `fk_password_reset_tokens_user_id`.
  - `authorization_requests`: `uq_…_uuid`, `uq_…_poll_token_hash`, `ix_…_user_id_status`, `ix_…_expires_at`, `ix_…_request_ip_created_at`, `ix_…_username_created_at`, `ix_…_approved_by_user_id`, `fk_…_user_id`, `fk_…_approved_by_user_id`.
  - `account_edit_lockouts`: `uq_account_edit_lockouts_user_id`, `fk_account_edit_lockouts_user_id`.
- The numbers follow merge order: if #88 or #89 merges first, renumber to the next free numbers right before merging (never edit a merged file).

### Entities and enums (`Pidgey\Model\`)

- `RefreshToken`, `PasswordResetToken`, `AuthorizationRequest` and `AccountEditLockout`: one promoted property per column, conversions through `Row`.
- `RevokedReason` (`Rotated`, `Logout`, `PasswordReset`, `ReplayDetected`, `AdminDenied`, `AdminEdit`) maps the `VARCHAR(32)` `revoked_reason` (nullable).
- `AuthorizationRequestStatus` (`Open`, `Approved`, `Denied`, `Logged`, `Expired`).
- Entity helper methods (`isExpiredAt($now)`, `isRevoked()`, …) are deferred to the endpoint issues that need them, as in #86.

### Repositories (`Pidgey\Repository\`)

Each repository has `create()` (re-reading the row by id) and `findById()`, plus the lookups by unique key. None of them is organization-scoped: these tables hang off `users`, and the lookups by digest/uuid are the spec'd cross-organization reads.

- `RefreshTokenRepository::create(string $tokenHash, int $userId, string $sessionUuid, DateTimeImmutable $issuedAt, DateTimeImmutable $expiresAt, DateTimeImmutable $startedAt)`, plus `findByTokenHash()`.
- `PasswordResetTokenRepository::create(string $tokenHash, int $userId, DateTimeImmutable $createdAt, DateTimeImmutable $expiresAt)`, plus `findByTokenHash()`.
- `AuthorizationRequestRepository::create(string $uuid, string $username, ?int $userId, string $pollTokenHash, string $requestIp, string $requestUserAgent, DateTimeImmutable $createdAt, DateTimeImmutable $expiresAt)`, plus `findByUuid()` and `findByPollTokenHash()`.
  - There is no status argument: a new request is always `open`, with `authorize_failed_attempts = 0`.
  - The uuid is generated by the caller.
- `AccountEditLockoutRepository::create(int $userId)`, plus `findByUserId()`.
  - It relies on the DB defaults (`failed_attempts = 0`, `locked_until` null, `created_at`/`updated_at`).
  - The upsert, `lockByUserId()` (`FOR UPDATE`) and the counter updates come with the account-edit endpoint issue.
- **Timestamps compared in PHP are explicit arguments**: `refresh_tokens.issued_at`, `password_reset_tokens.created_at` and `authorization_requests.created_at` are passed in by the caller (from `WallClock`), so start and expiry come from the same clock. The schema keeps `DEFAULT CURRENT_TIMESTAMP`.
  - Spec first: add this rule to the *Time* section of [persistence/repositories.md](docs/agents/specs/persistence/repositories.md).
- `Container` getters: `refreshTokenRepository()`, `passwordResetTokenRepository()`, `authorizationRequestRepository()` and `accountEditLockoutRepository()`.

### Test support

- `Fixtures` methods: `refreshToken()`, `passwordResetToken()`, `authorizationRequest()` and `accountEditLockout()`.
  - Each uses named overrides and plain SQL, with unique random 64-hex digests and UUIDs by default.
  - Each creates a user when no `userId` is given. `authorizationRequest()` accepts `userId: null` for an unknown username.
- `SchemaTest`: add the four tables to `TABLES`, with their columns, unique keys and foreign keys (reusing the helpers #86 adds). Also check the named plain indexes, since `authorization_requests` relies on composite ones.

## Tests

- Unit tests (`source/tests/unit/Model/`) for the four entities' `fromRow()`:
  - every column converted to its type;
  - nullable columns staying `null`;
  - a missing column, an unknown `status` and an unknown `revoked_reason` each throwing.
- Unit tests for the repositories' `Container` getters (memoized).
- Integration tests (`source/tests/integration/Repository/`, rollback isolation), covering every method:
  - not-found returning `null`;
  - the explicit timestamps round-tripping in UTC, including a non-UTC input;
  - defaults reflected after `create()`: `status = open`, `authorize_failed_attempts = 0`, `failed_attempts = 0`, the null event columns;
  - a duplicate `token_hash`, `uuid`, `poll_token_hash` or lockout `user_id` raising `PDOException`;
  - an unknown `user_id` raising `PDOException` (FK).
- No literal ids, and no DDL in repository tests.

## Security

- Only SHA-256 hex digests are stored and passed to repositories. No plain token reaches an entity, a fixture default or a log.
- A `security` agent review is required before merge.

## Out of scope

- Session rotation, replay detection, recovery, device-authorization state transitions and lockout logic, with their update/lock methods (endpoint issues).
- Entity helper methods.
